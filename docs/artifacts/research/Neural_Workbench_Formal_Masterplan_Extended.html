Neural Workbench as an object calculus for machine learning architecture design

This document formalises the AB framework as a design language for discretising machine learning systems into typed objects, transformations and interaction graphs. The aim is to support architecture search, model comparison and system construction by tracking input type, output type, information flow, computational cost and empirical capability.

1. Motivation

We seek a representation in which neural modules, adaptation mechanisms and agentic loops can be compared by their effects on information, rather than only by their historical names.

Standard architecture descriptions often mix several layers of explanation. A Transformer may be described as a stack of attention and feedforward modules, as an autoregressive language model, as a trained policy in an agent loop, or as an API component inside a larger tool system. These descriptions are all useful, but they live at different abstraction levels. The AB convention separates these levels, then defines the operators that move between them.

The central object is a typed module. It receives an input object, transforms it under constraints, and produces an output object. A system can then be studied as a graph of such transformations. This gives an engineering route to choose the best configuration relative to tracked parameters such as context length, memory, cost, compression, predictive accuracy, calibration, verifier reward and downstream task performance.

2. System view

The same formal grammar can describe a single layer, a model family, or a system such as iTrader. The relevant difference is the level at which the object and its deltas are defined.

3. AB objects

An AB object is a typed transformation equipped with an expected effect signature and an empirical capability profile. The type signature prevents invalid compositions. The effect signature supplies a prior over how the object may change information. The capability profile records what happened when the object was tested.

\\[ O_i = (\\mathcal X_i, \\mathcal Y_i, f_{\\theta_i}, E_i, C_i, \\Phi_i) \\] where \\(\\mathcal X_i\\) is the input type, \\(\\mathcal Y_i\\) is the output type, \\(f_{\\theta_i}\\) is the learned map, \\(E_i\\) is the expected effect vector, \\(C_i\\) is the cost model and \\(\\Phi_i\\) is the measured capability profile.

5. Input, output and effect signatures

The framework is useful only if each object is described from both sides: what it accepts and what it emits. A layer name alone is insufficient. A feedforward network may be a feature refiner, a bottleneck, a policy head or a value estimator depending on its input and output contract.

6. δAB operators

A δAB operator changes an existing object, a graph or a system. It may preserve the AB level, as in a LoRA update to a language model. It may also create a higher-level composite, as when an adapter bank is coupled to a router and a verifier.

\\[ \\delta : O_{\\theta} \\mapsto O'_{\\theta,\\phi} \\] \\[ W' = W + \\Delta W_{\\phi}, \\qquad \\Delta W_{\\phi} = \\frac{\\alpha}{r}BA \\]

7. Training and verifier deltas

Reinforcement learning methods are also δAB operators. They do not merely add a layer. They define a rule for changing a policy object from trajectories and rewards.

\\[ \\delta_t = r_t + \\gamma V(s_{t+1}) - V(s_t) \\] \\[ \\hat A^{GAE}_t = \\sum_{l=0}^{\\infty}(\\gamma\\lambda)^l\\delta_{t+l} \\] \\[ L^{PPO}(\\theta)=\\mathbb E\\left[ \\min(r_t(\\theta)\\hat A_t, \\operatorname{clip}(r_t(\\theta),1-\\epsilon,1+\\epsilon)\\hat A_t) \\right] \\]

8. Interaction graphs

An architecture is represented as a directed typed graph. Nodes are AB objects. Edges are typed information flows. δAB operators annotate either nodes, edges or the whole graph. This representation makes sequential, parallel, residual, gated and recursive arrangements comparable under a shared notation.

\\[ \\Gamma = (V,E,D,R) \\] where \\(V\\) are AB objects, \\(E\\) are typed edges, \\(D\\) are δAB operators and \\(R\\) are readout or reward functions.

10. Meta-strategy for configuration search

The framework becomes operational when it is used to search over configurations. A configuration is an AB graph with a set of δAB operators and a measured profile. The design problem is to choose a graph that satisfies constraints and maximises an objective over tracked parameters.

\\[ \\Gamma^* = \\arg\\max_{\\Gamma \\in \\mathcal G} J(\\Gamma; T, \\mathcal D, \\mathcal C) \\] \\[ J = \\alpha P_{task} - \\beta C_{compute} - \\gamma R_{risk} - \\xi I_{instability} + \\zeta V_{verified} \\] where \\(T\\) is the target task, \\(\\mathcal D\\) is data and \\(\\mathcal C\\) is the constraint set. 
Meta-strategy loop:
  define task and constraints
  select candidate AB objects
  compose graph Γ
  attach δAB operators
  train or evaluate
  update capability profile Φ
  choose, mutate or reject Γ

13. AB4 system formalisation

An AB4 system is a coupled learning or inference arrangement. It contains at least one AB3 model or learned policy, a memory or state substrate, an environment, a verifier or reward source and a policy for updating or selecting actions.

\\[ S_{AB4} = (\\mathcal O, \\mathcal D, \\mathcal M, \\mathcal E, \\mathcal V, \\mathcal R, \\Pi) \\] where \\(\\mathcal O\\) is the object set, \\(\\mathcal D\\) the δAB set, \\(\\mathcal M\\) memory, \\(\\mathcal E\\) environment, \\(\\mathcal V\\) verifiers, \\(\\mathcal R\\) reward functions and \\(\\Pi\\) the policy that controls interaction.

17. Closing statement

The AB framework is a practical notation for designing machine learning systems under constraints. It treats modules as typed objects, modern training methods as transformations, and agentic architectures as coupled systems with measurable capability profiles.
