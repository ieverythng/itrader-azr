Scope and implementation

The authoritative package migration remains Ray/RLlib 2.58.0, Gymnasium 1.2.2, and PyArrow 17.0.0. This work does not introduce an additional Ray version or unnecessary pandas, NumPy, or PyTorch upgrades. uv.lock is imported from the dirty Watson source snapshot.

The active trainer always selects the Ray 2.58 RLModule/Learner/EnvRunner stack; there is no rllib_api_stack selector or ModelV2/TorchPolicy fallback. The shared solver math is a PyTorch-only core, hosted by the native RLModule. Historical ModelV2/TorchPolicy adapters and Ray 2.58 legacy recipes are isolated in itrader/compat/rllib_legacy/; Ray 2.9 remains a separate runtime profile in itrader/compat/ray29/. The native adapter supports solver_mlp_film only and fails closed on other solver selectors or Ray versions. TaskSpec, ITraderEnv, RewardEngine, and online risk/execution seams are unchanged.

  • TorchRLModule forwards share the existing MLP-FiLM parameter layout and support PPO value prediction; the PyTorch-only core owns the shared trunk/state value readout used by the native ValueFunctionAPI.
  • Stable repository experiment inputs map to Ray's native Learner field names before RLlib configuration.
  • SingleAgentEpisode/MetricsLogger callbacks preserve project evidence and metric names; callbacks, reporting, and replay share one validated sum/count mean reducer.
  • Learner-side clipping diagnostics use the same forward pass as PPO loss.
  • Checkpoint inference, model identity, target-setting reconciliation, optimizer-moment preservation, and evaluation synchronization have native paths.
  • Both native replay entrypoints use one checkpoint replay-input contract that verifies actual checkpoint/data bytes and frozen source-panel identity before Ray starts.

Bounded validation

A synthetic parquet integration test exercises one real PPO update, learner diagnostics and metrics, checkpoint save/restore, deterministic action replay, changed-target donor restore reconciliation, and checkpoint-consistent evaluation synchronization for R0 and R4-v1 state modes. Module tests compare PyTorch-core/native logits and values and check native optimizer configuration. A separate real-Ray subprocess test invokes the official trainer CLI/Tune path for one update and checks completed run status, native stack identity, persisted reporting, and RLModule checkpoint structure. Both use synthetic data and are included in the repository test suite; full command and results are in the companion iteration record.

This is mechanical compatibility evidence only: no economic improvement, full-data readiness, PBT search effectiveness, or promotion is established. R1 remains unimplemented and the R0, R0 + R4-v1, R1, R1 + R4-v1 four-cell comparison is pending. The native migration is not an economic or representation result.

The pre-cutover feature-worktree suite completed with 416 passing tests. Required dependencies passed the healthcheck on Python 3.11.13, Ray 2.58.0, Gymnasium 1.2.2, PyArrow 17.0.0, and CPU Torch 2.3.1. Optional llama_cpp and transformers are not installed here.

Runtime notes

Ray 2.58 emits an RLModule deprecation warning from its checkpoint-restore internals; direct application-module construction uses the modern constructor. Ray documents the Learner API as alpha, so keep the exact runtime pin and bounded restore/evaluation probes in qualification. Historical reproduction uses the compatibility capsule or the exact source revision in the run manifest; it is not a selectable active trainer mode.
